= Services
:description: FF Logistic as three Spring Boot services behind a gateway.

Three services, `warehousing`, `transportation` and `routing`, each running one domain core from ff-logistic-shared, and a `gateway` that routes the edge's paths to them. The same ports as in the modulith, fulfilled over the network:

* a question to another area is an HTTP call, with a timeout and a fallback,
* an event goes into the outbox in the same transaction and reaches Kafka after commit; consumers are idempotent,
* each service applies its own area's migrations to the shared database.

[cols="1,1,3",options="header"]
|===
| Path | Port | What

| `contexts/warehousing` | 8082 | The warehousing core with the chassis
| `contexts/transportation` | 8083 | The transportation core with the chassis
| `contexts/routing` | 8084 | The routing core with the chassis
| `gateway` | 8081 | nginx: `/api/v1/wms/**`, `/api/v1/tms/**`, `/api/v1/geo/**` to their service; `/api/v1/me` to transportation
| `deploy/apps/*` | | Their values for the runtime's chart; the switch deploys them when `active: services`
|===

[[flows]]
== The flows, over the network

Flow 2 (S4): a delivery in transportation opens an inbound arrival in warehousing.

[mermaid]
....
flowchart LR
  TR["transportation<br/>ShipmentDelivered"] -->|"same transaction"| OB[("transportation.<br/>event_publication")]
  OB -->|"after commit, keyed by shipment"| K[["Kafka<br/>ff.logistics.tms.shipment-delivered"]]
  K -->|"group warehousing"| WC["warehousing<br/>messaging.DeliveriesToWarehouses"]
  WC --> IA["InboundArrivals.open"]
  WC -.->|"unreadable: at once<br/>failing: after 2 retries"| DLT[["….warehousing.dlt"]]
....

* *Transportation* owns its topics (`messaging.ShipmentTopics`) and keeps its outbox in the schema `transportation` (ff-base-events). `EVENTS_EXTERNALIZATION_ENABLED=false` keeps the events inside the service.
* *Warehousing* reads the message into a type of its own (`ShipmentDeliveredMessage`): it does not have transportation's classes, and ignores the fields it does not read. The topic's name and the fields are the contract.
* Both read the broker from `KAFKA_BOOTSTRAP_SERVERS` (`kafka:9092` in the cluster, `localhost:9094` from the IDE).
* The tests run a broker in the test JVM (`spring-kafka-test`): what one service sends and the other reads is checked for real, without Docker.

Flows 1 and 3 (S5), between routing and transportation:

* *Flow 1, a question*: transportation's `distances.RoutingDistances` fills the port `DistanceLookup` with `GET http://routing:8084/api/v1/geo/distance`, relaying the caller's token, with 1 s to connect and 2 s to answer. No answer in time, and the core falls back to the straight-line estimate; the leg records which (`ROUTING` or `ESTIMATE`) (xref:ff-logistic::architecture.adoc#flow-1[on each side]).
* *Flow 3, an event*: routing keeps its own outbox (schema `routing`) and publishes `RouteStopCompleted` to `ff.logistics.geo.route-stop-completed`, keyed by route plan. Transportation's `messaging.CompletedStops` reads it in the group `transportation`, with its own dead-letter topic (`….transportation.dlt`) (xref:ff-logistic::architecture.adoc#flow-3[on each side]).

The three applications differ only in which core they hold, their port and their name; their `application.yml` files repeat the database and token settings, as each service's configuration is its own. That repetition is one of the costs the comparison counts.

[source,bash]
----
./build.sh                                              # after base and shared are installed
for s in warehousing transportation routing; do
  docker build -t ghcr.io/ffetih/ff-logistic-services/$s:local contexts/$s
  k3d image import ghcr.io/ffetih/ff-logistic-services/$s:local -c ff-logistic
done
docker build -t ghcr.io/ffetih/ff-logistic-services/gateway:local gateway
k3d image import ghcr.io/ffetih/ff-logistic-services/gateway:local -c ff-logistic
----
